===== [A8] incident: the pipeline on main replaced the M3 stack with M2, 00:30-00:35 UTC =====
For the "follower down" variant, node-c was stopped (ec2 stop-instances, 00:02 UTC; SSM can't
reach the shard nodes, which have no route to it) and workload A started at 00:04.
At 00:30 PR #1 (ci-docs-check) was merged into main. The ci-cd pipeline deployed main, still
the M2 code, onto the same stack velmakina-kv-app: CloudFormation removed NodeA/B/C and the
benchmark client and created M2's Shard1/Shard2 (stack events 00:33-00:35). The client ran
the three runs but was terminated before SSM could return them: the follower-down results
are lost (the SSM command shows "Undeliverable"). To be run again in the next lab session.
Lesson: while M3 is deployed by hand, nothing is merged into main (the pipeline and the
manual deploys share one stack).

No replica reached the coordinator for 7 minutes: the coordinator's group allowed 8080 only
from my laptop's /32. Cause, a template bug: the pipeline deploys with
CLIENT_CIDR=10.20.0.0/16 (no ALLOWED_CLIENT_CIDR variable set), so the group's two rules
("from the VPC" and "from the client") were the same rule, which EC2 keeps once. My deploy
changed the client CIDR to my /32: CloudFormation revoked the old client rule 10.20.0.0/16,
which was also the VPC rule. Fixed by hand for this run (01:08), then gone with the stack:
$ aws ec2 authorize-security-group-ingress --group-id <coordinator-sg> --ip-permissions tcp 8080 10.20.0.0/16
ready within 10 s. A template fix is still to do.
