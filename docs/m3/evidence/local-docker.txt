Local cluster in Docker: coordinator + 2 shards × 3 replicas (r1a..r2c) from one image
(docker-compose.yml), W = 2, R = 2. 2026-11-25, Docker 28.4.0, image capstone-kv:local
(8.93MB), code at 3d9820d plus the uncommitted group-5 changes.

Run:  docker compose down -v && make local-up && scripts/failure-tests.sh
Every check prints ok or FAIL; the script stops at the first FAIL. Sections map to the
scenarios of openspec/changes/m3-replication/specs/{replication,quorum-reads}.

===== [M3-L0] what the first runs found and fixed =====
1. First leader not the preferred one. Replicas 1b and 1c reported before 1a, formed a
   majority, and 1b became shard-1's first leader although KV_LEADERS names 1a (ADR-0020:
   the two shards' first leaders on different nodes). Fix: a set gets its first leader once
   all its replicas have reported, or once a majority has waited one timeout (15 s), so a
   dead replica can't block a start.
2. Ready before the leader knew. /health said ready as soon as the coordinator had picked
   a leader, but the leader learns it only from its next heartbeat answer (up to 5 s); until
   then it refused writes (409 -> 503). Fix: ready requires each leader to have confirmed its
   epoch in a heartbeat.
3. (script) The 504 scenario first used a key that hashes to shard-2, where all replicas
   were up, so the put committed. Fixed by using a known shard-1 key.
Both code fixes have unit tests (TestFirstLeaderChoice, TestNotReadyUntilShardsRegister).
